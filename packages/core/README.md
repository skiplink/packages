# @skiplink/core

Violation identity and baseline diffing for [Skiplink](https://skiplink.dev).

This is the shared foundation the CLI, the GitHub Action and the test-framework
adapters are built on. You rarely install it directly — install
[`@skiplink/cli`](https://www.npmjs.com/package/@skiplink/cli) or
[`@skiplink/playwright`](https://www.npmjs.com/package/@skiplink/playwright)
instead. It is published separately because everything in it is the kind of code
that must have exactly one implementation.

```bash
npm install @skiplink/core
```

## What it does

**Violation identity.** Gives every accessibility violation a stable fingerprint,
so the same problem on the same element is recognisable across runs. This is what
makes "fail only on new violations" possible.

**Baseline diffing.** Compares a scan against a committed baseline file and
classifies each violation as new, accepted, drifted or fixed.

## Why it is a separate package

Skiplink scans pages by two different routes. Public URLs go through the hosted
API, which runs axe-core on our infrastructure and fingerprints in Go. Private
pages — behind a login, on `localhost`, three steps into a checkout — are scanned
by the test-framework adapters, which run axe-core in your own browser and
fingerprint here in JavaScript.

Both write to the same baseline file. If the two implementations disagreed by a
single character, a violation accepted through one route would come back as new
through the other, every build would fail for reasons nobody could see, and it
would look like the scanner was flaky.

So the JavaScript implementation is tested against a file of vectors generated by
the Go one. The vectors deliberately include the cases where two languages quietly
stop matching:

- **`\s` is not the same set.** Go's matches `[\t\n\f\r ]`. JavaScript's also
  matches U+00A0, U+2009, U+3000 and U+FEFF — so the obvious `/\s+/g` collapses
  non-breaking spaces that Go leaves alone, and non-breaking spaces appear on
  every page that has a price or a name on it.
- **Truncation units differ.** Go counts bytes of UTF-8. `slice(0, 120)` counts
  UTF-16 code units. For any non-ASCII text these are different strings.
- **Truncation can split a character**, producing invalid UTF-8 that JavaScript
  cannot represent at all. Both sides back off to a character boundary.
- **Lowercasing genuinely disagrees.** Go maps U+0130 (`İ`) to `i`; JavaScript
  produces `i` followed by a combining dot. JavaScript lowercases a trailing `Σ`
  to `ς`, Go always to `σ`. Both are correct for text and neither can be made to
  match the other, so both sides fold ASCII only — a fingerprint needs identical
  bytes far more than it needs Unicode case semantics.

## API

### Fingerprints

```js
import { fingerprint, fingerprintLoose } from '@skiplink/core/fingerprint';

fingerprint('color-contrast', '.hero__title');
// 'f_1519fd36' — rule plus normalised selector

fingerprintLoose('color-contrast', '<p class="hero__title">Ship faster</p>');
// 'f_...' — rule plus the element's text
```

`fingerprint` is exact: it changes if the selector changes. `fingerprintLoose`
keys on the element's text instead, so it survives a restyle that renamed every
class, at the cost of colliding across repeated instances of the same component.
Baseline matching tries exact first and falls back to loose, which is why the
loose one is safe to have.

The exact fingerprint deliberately does **not** try to guess which parts of a
selector are build output. It used to: a heuristic collapsed runs that looked like
a bundler hash, and it also matched ordinary BEM element names, so `.hero__title`
and `.hero__subtitle` shared one fingerprint. A baseline entry for either then
absorbed a new violation on the other and the gate reported green on a broken
page. Class churn is what the loose fingerprint is for.

### Baselines

```js
import { loadBaseline, saveBaseline, baselineFrom, diff, shouldFail }
  from '@skiplink/core/baseline';

const baseline = await loadBaseline('.skiplink/baseline.json'); // null if absent
const outcome = diff(scanResults, baseline);
// { isNew, accepted, drifted, fixed, total }

const verdict = shouldFail(outcome, 'new');
// { fail: boolean, reason: string, blocking: Violation[] }
```

`diff` returns four sets, and the distinctions matter:

| | |
|---|---|
| `isNew` | Not in the baseline. The only set that ever fails a build. |
| `accepted` | Matched a baseline entry by exact fingerprint. |
| `drifted` | Matched only by text, because the selector changed. Reported, not failed — a restyle is not a regression. |
| `fixed` | In the baseline but not in this run. Never failed on: a scan of one URL must not conclude that violations on twelve others were fixed. |

Baselines key on URL **path**, not the whole URL, so one file works across
`localhost:3000`, a per-branch preview deployment and production. Query strings
are part of identity; trailing slashes are not.

A loose match is consumed once per baseline entry. Without that, one accepted
violation could absorb any number of new ones and the gate would stay green while
the page got steadily worse.

### axe-core normalisation

```js
import { flatten, tagsForStandard, wcagFromTags } from '@skiplink/core/axe';

flatten(axeResults.violations);
// one entry per offending element, with selector, html, message, wcag, help_url

tagsForStandard('wcag22aa');
// ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa']
```

One violation per element rather than per rule: a rule failing on nine elements is
nine things to fix and nine independently resolvable findings.

`tagsForStandard` returns `undefined` for a name it does not recognise, not an
empty array — axe-core reads an empty tag list as "run every rule", which is the
opposite of refusing a typo. The map is checked against the Go one by a test, so a
standard cannot come to mean different rules depending on which route ran the scan.

### Reports

```js
import { human, json, markdown, githubAnnotations } from '@skiplink/core/report';

console.log(human(outcome, verdict, { scans }));
```

The formats the CLI prints, for tools that want the same output: `human` for a
terminal, `json` for machines, `markdown` for a pull-request comment or job summary
(pass `runUrl` to link the CI run), and `githubAnnotations` for `::error` /
`::warning` lines, one per new violation. All take the result of `diff`; all but
`githubAnnotations` also take the verdict and the scans the diff came from.

## Standards

`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` (the default),
`section508`, and `all`. `all` includes axe-core's best-practice rules, which are
not WCAG success criteria — failing a build on those is a choice, not a compliance
requirement.

## Accuracy

Automated testing detects a subset of WCAG success criteria; published estimates
range from roughly 13% to 57% depending on whether you measure by success criteria
or by issue volume. Keyboard order, focus management, whether alt text is
*accurate*, and whether a custom widget behaves the way its role promises all need
a person. No output of this package is a statement of conformance.
